# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

### Setup
```bash
pyenv shell 3.12.11
python -m venv venv
source venv/bin/activate
pip install -r requirements.txt
```

### Run — CLI mode
```bash
python main.py
```

### Run — Web dashboard
```bash
uvicorn app.server:app --port 8000
```
Must be run from the project root (not from inside `app/`), because `DataEngineeringState`'s default paths (`data/`, `reports/`, `data/warehouse.db`) resolve relative to cwd.

### Switch active dataset
```bash
python switch_dataset.py [fuzzy|olist|mock|amazon]
```
Without an argument, switches to the mock dataset. Files in `data/` are the active set; others live in `data/{name}_backup/`.

### Run tests
```bash
python -m pytest tests/
# or single test class:
python -m unittest tests.test_flow.TestFlowArchitecture
```

## Architecture

### Pipeline — CrewAI Flow (`crew.py` + `pipeline/`)

`DataEngineeringFlow` extends `Flow[DataEngineeringState]`. Each decorated method is a pipeline step:

```
profile_datasets (@start)
  → assess_quality (@listen)
    → check_quality_threshold (@router)  ← human-in-the-loop gate
      → design_schema (@listen "proceed_pipeline")
        → plan_transformations (@listen)   ← SQL generation + retry loop
          → run_analytics (@listen)
            → compile_final_report (@listen)
```

`DataEngineeringState` (Pydantic model, `pipeline/core/state.py`) is the shared state: `files`, `profiling_results`, `quality_report`, `star_schema`, `clean_sql`, `kpi_report`, `entity_map`, `source_row_counts`, `primary_fact_table`, `verified_metrics`. Token usage is tracked separately by `TokenReporter` (per-run, held on `StepContext`), not in the state model.

**Each pipeline step creates its own `AgentFactory` + `TaskFactory` + `Crew` — agents are not shared across steps.**

### Agent & Task factories

- `agents/factory.py` — `AgentFactory` instantiates CrewAI `Agent` objects. Provider auto-selected from `PIPELINE_MODEL`:
  - `ollama/*` → `OllamaProvider` (uses `base_url`, adds `num_ctx: 8192`)
  - `bedrock/*` → `BedrockProvider` (sets `drop_params=True`, special-cases Nemotron)
  - anything else → `CloudProvider`
- `tasks/factory.py` — `TaskFactory` reads task prompts by merging every YAML file in `config/tasks/` (one file per pipeline stage: `quality.yaml`, `intent.yaml`, `schema.yaml`, `transform.yaml`, `analytics.yaml`, `report.yaml`), injects agents. All task descriptions use `{placeholder}` interpolation resolved by `crew.kickoff(inputs=...)`.
- Agent roles/goals/backstories in `config/agents.yaml`; task descriptions split across `config/tasks/*.yaml` by pipeline stage.

### Tools (`tools/`)

All tools extend `crewai.tools.BaseTool` with a Pydantic `args_schema`. Non-pydantic state uses `PrivateAttr`.

`ToolRegistry` is the DI container — instantiate it with `data_dir`, `chroma_db_path`, and `db_path`, then call `get_db_tools()` / `get_memory_tools()`. `AgentFactory._filter_tools()` selects tools by name for each agent.

Key tools:
- **`RunDuckDBQueryTool`** — connects to `db_path`, re-registers all source files as views, rewrites filename references, executes SQL. Used by agents that need to query data.
- **`ProfileCSVFileTool`** — Polars streaming profiler: detects encoding, computes null/unique counts via lazy eval, infers column types via `TypeInspector`, detects schema shifts via `SchemaShiftDetector`.
- **`ReadCSVPreviewTool`** — reads first N rows of any supported file (CSV/Excel/JSON).
- **`SavePastExecutionTool` / `SearchPastExecutionsTool`** — ChromaDB-backed memory under `.chroma/`.

### `DatabaseService` (core SQL engine)

- `sanitize_table_name(filename)` — strips extension, replaces non-alphanumeric chars with `_`. This is the canonical name used in all DuckDB queries.
- `register_sources(conn, data_dir)` — loads every CSV/xlsx/json in `data_dir` as a Polars DataFrame and registers it as a named DuckDB view. Column names are stripped of whitespace.
- `execute_sql_script(db_path, script_path, data_dir)` — strips markdown fences (` ```sql ` blocks), splits on `;` using a state-machine parser (handles strings, comments), runs each statement, returns list of errors. Calls `_replace_table_references` on each statement before execution.
- `_replace_table_references` — rewrites bare filename or word-split references (e.g., `"Amazon Sale Report.csv"` or `Amazon_Sale_Report`) to the sanitized table name.

### Warehouse build loop (`TransformStep` in `pipeline/steps/transform.py`, `crew.py`'s `plan_transformations` step)

Building the warehouse is a **per-table** loop, not a single generate-and-retry-the-whole-script pass:

1. **Schema plan** — the Warehouse Architect returns a JSON table list (`create_schema_plan_task`), Dim_ tables before Fact_ tables.
2. **Per-table build** (`TableBuilder.build_all`, `utils/sql_executor.py`) — for each table: generate its SQL (`create_generate_table_sql_task`), execute it, verify it exists and (for Fact_ tables) has >0 rows. On failure, retry with the error fed back via `create_fix_table_sql_task`, up to `MAX_RETRIES = 3` attempts; a table that still fails after that is **skipped**, not fatal to the whole run.
3. **Primary fact selection** — `WarehouseMetrics.select_primary_fact` picks the primary Fact_ table by e-commerce entity role (revenue/transaction priority from `entity_map`), not by row count.
4. **Retention check** (`TableBuilder.run_retention_check`) — total Fact_ rows must be ≥70% of (total source rows − total Dim_ rows). Below that, a "Data Loss Alert" is logged as a warning (`_check_retention` in `TransformStep`), not a hard abort.
5. **Deterministic structural validation** (`WarehouseMetrics.run_structural_validation`) — PK uniqueness, fact fan-out, revenue-sign checks. On FAIL, only the *named failing tables* are corrected: the Warehouse Architect rebuilds each via `TableBuilder.fix_table` → `create_fix_table_sql_task` (same fix-task machinery as step 2, now driven by a structural failure instead of an execution error), then validation re-runs. Up to `MAX_VALIDATION_FIX = 2` corrective rounds; if it still FAILs after that, the run raises `RuntimeError` and aborts.

The fix task returns corrected SQL for **one table only** — never the whole script.

### Entity Classifier (`tools/entity_classifier.py`)

`EntityClassifier.classify(columns, row_count, filename)` runs deterministically (no LLM) to classify each source file as one of: `orders`, `order_items`, `products`, `customers`, `sessions`, `pageviews`, `refunds`, `financials`, `inventory`, `campaigns`, `unknown`.

Scoring: required signal groups (+10 each), supporting signals (+2 each), disqualifying signals (−6 each). Confidence = score / max_possible. Returns `entity`, `confidence`, `grain`, `matched_signals`, `notes` (set if runner-up is within 80% of winner score).

Called in `profile_datasets` after the LLM profiling run; the resulting `entity_map` is injected into the schema design and transformation task prompts as **ground truth** (agents are told not to re-classify).

### Human-in-the-loop (`tools/human_loop.py`)

`HumanLoopService` uses a strategy pattern:
- **CLI mode** (default): `CLIApprovalStrategy` — prompts `stdin`.
- **Web mode**: `WebApprovalStrategy` — wraps a callback. `app/server.py` wires `RunManager.request_approval()` as the callback, which blocks a `threading.Event` until the frontend POSTs to `/api/approve` or `/api/reject`.

### Web server (`app/server.py`)

`RunManager` tracks pipeline state (`idle` / `running` / `waiting_approval` / `completed` / `failed`). It patches `sys.stdout` and `sys.stderr` to a `LogBuffer` for the duration of the run, so `/api/status` can stream logs back to the browser.

The pipeline runs in a daemon thread. The frontend polls `/api/status` every second. `_STEP_MARKERS` maps log lines to the 6-step progress indicator in the UI.

Static files are mounted at `/static`; `GET /` serves `app/static/index.html`.

### LLM configuration

| Env var | Default | Purpose |
|---|---|---|
| `PIPELINE_MODEL` | `ollama/gemma4:31b-cloud` | Model passed to CrewAI `LLM` |
| `PIPELINE_BASE_URL` | `http://localhost:11434` | Ollama endpoint (ignored for non-Ollama models) |
| `SQL_MODEL` | _(none — falls back to PIPELINE_MODEL)_ | Model for SQL generation (Warehouse Architect) |
| `SQL_AWS_REGION` | _(none)_ | AWS region for SQL model if using Bedrock |
| `BI_MODEL` | _(none — falls back to PIPELINE_MODEL)_ | Model for analytics engineer (BI agent) |
| `BI_AWS_REGION` | _(none)_ | AWS region for BI model if using Bedrock |

### Output reports (`reports/`)

| File | Producer |
|---|---|
| `profiling_report.json` | `profile_datasets` (includes `_entity`, `_entity_confidence`, `_entity_grain` keys) |
| `quality_report.md` | `assess_quality` (must contain `Quality Score: N/100`) |
| `schema_design.md` | `design_schema` |
| `transformations.sql` | `plan_transformations` (overwritten on each retry) |
| `validation_report.md` | Deterministic structural validation (`WarehouseMetrics`, must end with `Validation Status: PASS` or `FAIL`) |
| `kpi_report.md` | `run_analytics` |
| `executive_summary.md` | `compile_final_report` |
| `token_usage_report.json` | `compile_final_report` (keyed by agent role) |
